# 팀 프로젝트 평가 기준

2026-11-25에 확인한 Bugeun Kim 교수 공지 기준. 총 30점이며 향후 구현·검증·시연 준비에 적용한다.

| 항목 | 배점 | 평가 방식 및 기준 |
| --- | --- | --- |
| 진행 상황 제출 | 5 | 모든 중간 진행 상황을 마감 전에 제출했는지 확인. 부분 점수 있음. 중간 내용과 최종 결과가 같을 필요는 없음. |
| 프로젝트 요구사항 충족 | 5 | 지시사항 준수, 특히 화면 수 확인. 부분 점수 있음. |
| 창의성 | 5 | 동료가 시연과 직접 사용 경험으로 평가. 유용성 2, 접근성 1, 아이디어 2. |
| 복잡도 | 5 | 동료가 앱 자체로 평가. 개발 난이도 2, 목적에 적절한 기능 2, 단순성/완성도 1. |
| 오류 처리 | 10 | 동료 평가. 적절한 오류 안내/대안 5, 오류 포착·처리 5. |

## 창의성 세부 기준

- 유용성(2): 0 = 유용하지 않음, 1 = 소수에게 유용, 2 = 많은 사람에게 유용.
- 접근성(1): 0 = 현실의 사용 장벽을 고려하지 않음, 1 = 고려함.
- 아이디어(2): 0 = 동일 기능 앱을 쉽게 찾음, 1 = 거의 유사한 앱을 찾을 수 있음, 2 = 다른 앱과 비교해 고유한 기능 제공.

## 복잡도 세부 기준

- 난이도(2): 한 달 내 개발에 0 = 1명으로 충분, 1 = 2~3명 필요, 2 = 4~5명 필요.
- 기능(2): 앱 목적 달성에 0 = 부적절, 1 = 일부 부족하거나 지나치게 특수함, 2 = 적절함.
- 단순성/완성도(1): 추가 개선을 제안할 수 있는지에 0 = 가능, 1 = 현재로 충분.

## 오류 처리 세부 기준

- 오류 안내(5): 0 = 안내 없음, 3 = 가끔 안내/대안 제공, 5 = 필요한 안내/대안을 모두 적절히 제공.
- 별도 메시지가 없어도 대체 경로를 제공하면 올바른 안내로 인정한다.
- 오류 처리(5): 0 = 모든 경우 충돌, 3 = 일상 사용의 오류 처리, 5 = 상상 가능한 거의 모든 경우 처리.
- 예시이며 이에 한정되지 않는 시험 사례: 통신 도중 Wi-Fi 끄기, 매우 긴 텍스트 입력으로 위젯 깨뜨리기, 입력 제한 검증, 화면 방향 전환.
- 앱 오류로 보지 않는 사례: 형식은 올바르지만 내용이 잘못된 서버 응답, AI 환각, 서버의 네트워크/로직 실패. 다만 클라이언트의 연결 실패 안내·재시도 등은 여전히 점검한다.

## 앞으로의 작업에 적용

- 오류 처리 배점이 가장 크므로 기능 구현 시 실패·복구 흐름까지 검토한다. 통신 중 단절, 긴 텍스트, 입력 경계값, 가로/세로 전환을 변경 범위에 맞게 확인한다.
- 기능 수 자체보다 앱 목적에 필요한 기능의 완성도, 실제 유용성, 고유성, 사용 장벽을 고려한다.
- 시연과 직접 사용에서 실제 동작을 확인할 수 있도록 준비하고 데모 데이터·미연동 기능을 구분한다.
- 화면 수의 정확한 최소 기준과 제출 마감일은 이 공지에 없다. 별도 과제 지시에서 확인해야 하며 임의로 정하지 않는다.
- 중간 제출 여부는 Git 커밋/푸시만으로 확정하지 않는다. 별도 제출 기록이 있어야 완료로 판단한다.
